# Project 1 — Application Engine

## Local setup (Claude Code)

This project's origin is claude.ai Projects, which provided a sandboxed environment with preinstalled packages and fixed paths (`/mnt/user-data/outputs/`, `/home/claude/`). In Claude Code, run `npm install` here first (installs `docx`, used by all four templates in `templates/`: `resume-template.js`, `cover-letter-template.js`, `cold-outreach-letter-template.js`, `thank-you-letter-template.js`). Generated documents go to `outputs/` at the repo root (gitignored) — this replaces the old `/mnt/user-data/outputs/` convention referenced in skill instructions. No automated DOCX validator is available locally (the sandbox's `/mnt/skills/public/docx/...` validator doesn't exist here) — visually check generated `.docx` files before delivering them.

## Purpose

Generates tailored job-application artifacts (gap analyses, resumes, cover letters, interview prep, salary research) for Sarah Ashford.

## Source of truth

This project does not own career facts. Skills must read `app-engine-bundle.md` as the single source of truth — never load Project 2's `profile-facts.md`, `Resume_Snapshot.md`, `skills-summary.md`, or `github-repos.md` directly, even though those files are readable from here. If the bundle looks stale or wrong, that's a Project 2 problem — flag it there, don't patch around it locally.

## Bundle generation trigger

`app-engine-bundle.md` is generated by `profile-hub-bundle-generator_SKILL.md`, which lives in **Project 2 only**. This project cannot regenerate its own bundle.

Check the bundle's `bundle_version` and `generated` date header before relying on it for anything cert-status- or resume-sensitive. If a change was made in Project 2 (cert earned, gap resolved, resume edited, portfolio project added) and this bundle wasn't refreshed afterward, tell the user to run "generate bundles" in Project 2 and reimport before proceeding — don't silently work from stale data.

## Conventions

- New skill files follow the `*_SKILL.md` naming pattern (or `.skill` for the router).
- `JobSearch_KeywordStrategy.md` lives in `reference/` here rather than Project 3, because it's job-search strategy, not presence/identity content — treat this as precedent for future placement calls between P1 and P3.
- Generated output (`*.docx`, `*.pdf`, `node_modules/`, `app-engine-bundle.md`) is gitignored — never commit it.
- **Exception:** `reference/star-bank.md` write-back via `interview_prep.py --update-star-bank` (see `skills/interview_prep/SKILL.md` Step 5) is deliberately not disposable output. It mutates a real, hand-maintained reference file — updating `last_used`/`used_for` metadata on existing stories — not regenerating something derived. Those mutations should eventually be committed by the user, unlike everything else in this bullet.
- `app-engine-bundle.md` is ~46KB / ~11.5K tokens. Don't instruct a skill to "load `app-engine-bundle.md`" wholesale unless it genuinely needs the resume/career-history prose (the `## Resume` heading onward — cover letter, resume, and interview-prep generation legitimately do). If a skill only needs facts (cert status, differentiators, gaps, portfolio, ATS keywords, AI-200 coverage, Copy Fragments) or just contact info, use `python project-1-application-engine/scripts/extract_bundle_sections.py facts` / `section "<heading>"` / `contact` instead — see `salary_research`, `cold_outreach_recruiter_letter`, `post_interview_thank_you_letter`, `azure_focused_net_developer`, and Project 2's `learning_plan_gap_analysis` for examples. Note the bundle has two headings both named `## Key Differentiators` (a short facts-section list and a longer resume-bullet version); `section` always matches the first — the facts one.

## Known limitations

- `render_md_bundles.py` writes `app-engine-bundle.md` directly to its canonical location here — there's no separate manual reimport step to forget. What *can* still go stale silently is the regeneration itself: nothing enforces that "generate bundles" was actually re-run after a Project 2 source edit. `project-2-profile-learning-hub/scripts/check_bundle_freshness.py` (wired into the local pre-commit hook) catches this by comparing the bundle file's mtime against its P2 sources' mtimes — but it only fires when a Project 2 commit is made, so an edit that's never committed (or committed elsewhere without triggering that hook) won't be caught. Treat a stale-looking bundle as a prompt to re-run "generate bundles" in Project 2, not as something this project can self-correct.
- Skills/reference docs that hardcode a bundle-tracked number (course counts, cert status) instead of loading it live will silently drift out of sync as the bundle regenerates. This was found and "fixed" by hand in `reference/gap-coaching.md`, `employment-research-SKILL.md`, and `fullstack-net-profile-resume-SKILL.md` during an Aug 2026 audit — and a second Aug 2026 audit found it had already crept back into `fullstack-net-profile-resume-SKILL.md` (a stale "AZ-204 in progress" claim) and `employment-research-SKILL.md` (a hardcoded "19 courses" instead of `{github_copilot_course_count}`), proving prose reminders alone don't hold. The `## Copy Fragments` section in `app-engine-bundle.md` exists specifically to reduce this: prefer `{fragment_name}` placeholders filled from the bundle over embedding a literal number in new skill/reference content. There is now also an automated guardrail — `project-2-profile-learning-hub/scripts/check_skill_hardcoding.py` — that scans every project's `skills/*/SKILL.md` for cert-status claims and course counts that contradict the current source files; run it after editing any skill and before considering the edit done.
