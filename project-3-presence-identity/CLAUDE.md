# Project 3 — Presence & Identity

## Purpose

Handles LinkedIn, GitHub profile, and job board bio/presence updates for Sarah Ashford.

## Source of truth

Skills must read `presence-bundle.md` as the single source of truth for current content and cert status before writing any field. Never load Project 2's raw source files directly.

## Bundle generation trigger

`presence-bundle.md` is generated by `profile-hub-bundle-generator_SKILL.md`, which lives in **Project 2 only**. This project cannot regenerate its own bundle.

The bundle is GitHub-safe (no phone/email) and stays in the local workspace — committed to the private `claude-projects` repo under `project-3-presence-identity/presence-bundle.md`. Project 3 skills read the local file directly as the source of truth — there is no public raw-URL fetch step (the repo is private and `raw.githubusercontent.com` would 404 for anonymous consumers). If cert status or profile content was recently changed in Project 2, confirm `presence-bundle.md` was regenerated and the new version is present at this path.

## Folder / file responsibilities

| Path | Role |
|---|---|
| `presence-bundle.md` | Authoritative profile data — headline, summary, cert status, skills, portfolio, differentiators, and per-employer experience bullets (`## Professional Experience`, rendered from `Resume_Snapshot.md` via the bundle's typed `experience` list — bullet-for-bullet identical to the resume, not a paraphrase). Includes a `## Copy Fragments` section (`course_count_sentence`, `cert_status_short`, `azure_course_lab_sentence`, `github_copilot_course_count`, `leadership_course_count`) that both skills below fill into their draft copy instead of hand-embedding numbers. |
| `skills/update_linkedin_profile_SKILL.md` | LinkedIn field updates (About, Open to Work, Experience, Skills, Certifications, Courses, Featured) |
| `skills/update-github-profile-SKILL.md` | GitHub field updates (bio, status, profile README, pinned repos) |
| `skills/update_job_board_profiles/SKILL.md` | Indeed & ZipRecruiter field updates (headline, summary, skills, job preferences); also checks the uploaded resume file's freshness against the bundle, since these two platforms parse the resume into most of the profile |
| `skills/update_jobgether_profile/SKILL.md` | Jobgether field updates (title, about/bio, skills, job preferences); same resume-freshness check, since Jobgether's match scoring leans on the uploaded resume too. Built without a confirmed live account to verify field names/limits against — check the skill's own warning note the first time it's used |
| `skills/update_pluralsight_profile/SKILL.md` | Pluralsight field updates (bio/tagline, job title, location, links) — smaller surface since it's not a job board and Skill IQ/course data updates itself |

## Conventions

- All five skills include post-exam update checklists to keep every surface in sync after certification results — any new presence skill added here should follow the same "check cert status, then update this surface" shape.
- Unlike LinkedIn/GitHub, Indeed/ZipRecruiter/Jobgether/Pluralsight publish no fixed field character limits — those skills state practical (not enforced) length targets instead, and say so explicitly rather than implying a real platform cap.
- Each skill writes its own paste-ready draft file at generation time (`linkedin-update-draft.md`, `job-board-profile-update-draft.md`, `jobgether-profile-update-draft.md`, `pluralsight-profile-update-draft.md`) rather than sharing one file across skills — keep that one-file-per-skill boundary for any future presence skill too.
- Draft copy (About text, Bio line, README "Currently" line, etc.) should use `{fragment_name}` placeholders filled from `presence-bundle.md`'s Copy Fragments section rather than a literal number — an Aug 2026 audit found both skills had gone stale for months (still describing AZ-900 as "in progress" after it was certified, course counts less than half the current total) because the numbers were hand-typed and never revisited after the bundle moved on.
- `JobSearch_KeywordStrategy.md` is intentionally tracked in Project 1's `reference/`, not here — it's job-search strategy, not presence/identity content. Don't duplicate it into this project.

## Known limitations

- `render_md_bundles.py` writes `presence-bundle.md` directly to its canonical location here (no manual copy step). `project-2-profile-learning-hub/scripts/check_bundle_freshness.py`, wired into the local pre-commit hook, flags this file as stale if any Project 2 source (`profile-facts.md`, `Resume_Snapshot.md`, `skills-summary.md`, `github-repos.md`) was edited more recently than it — but only fires on a `git commit`, so it won't catch drift between commits. If a downstream LinkedIn/GitHub skill reads stale content, the first thing to check is whether the local file at `project-3-presence-identity/presence-bundle.md` matches what was just regenerated in Project 2.
